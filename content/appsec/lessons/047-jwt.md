    const AUD = "telemetry-api";
    const ALLOWED_ALGS = ["HS256"];

    type Header = { alg?: string; typ?: string };
    type Claims = { iss?: string; aud?: string | string[]; exp?: number; nbf?: number; sub?: string };

    function checkClaims(header: Header, claims: Claims, now: number): string {

## Muammo

JWT (JSON Web Token) so'nggi yillarda "authentication = JWT" degan odatiy javobga aylanib qoldi. Yangi loyihada Auth qatlami kerak bo'lsa, ko'pchilik `jsonwebtoken` ni o'rnatib, `sign` va `verify` ni chaqiradi va ishni tugatilgan deb biladi. Lekin JWT tayyor autentifikatsiya tizimi emas: u ma'lumotlarni imzolangan shaklda tashish formati. Undan qanday foydalanish haqidagi qarorlar (qaysi algoritm, qaysi claim'lar tekshiriladi, qancha yashaydi, qanday bekor qilinadi) dasturchi zimmasida.

Bu qarorlar xato bo'lsa, oqibatlar og'ir. Ko'p uchraydigan holatlar: verifier token header'ida yozilgan algoritmga ishonadi (hujumchi `none` yoki boshqa algoritmni tanlaydi); imzo tekshiriladi, lekin `exp`, `iss`, `aud` tekshirilmaydi; token'ga maxfiy ma'lumot yoziladi va uni "imzolangan, demak xavfsiz" deb o'ylashadi; foydalanuvchi parolini almashtirgandan keyin ham eski token bir hafta ishlaydi. RFC 8725 (JWT Best Current Practices) aynan shu nosozliklar yig'indisi uchun yozilgan: u bir qator hujumlarni sanab, har biriga amaliy tavsiya beradi.

Ikkinchi nuqta: JWT ko'pincha kerak emas. Bitta brauzer ilovasi va bitta backend uchun oddiy server sessiyasi (46-dars) soddaroq, bekor qilish oson va hujum yuzasi kichik. Bu dars JWT'ni to'g'ri ishlatishni ham, uni qachon tanlamaslikni ham ko'rsatadi.

## Asosiy g'oya

### Tuzilishi

Imzolangan JWT (JWS compact serialization) nuqta bilan ajratilgan uch qismdan iborat: `header.payload.signature`. Har qismi base64url bilan kodlangan. Header token turi va algoritmni (`alg`) bildiradi, payload claim'larni (JSON), imzo esa header va payload ustida hisoblanadi.

RFC 7519 ro'yxatdan o'tgan claim'larni belgilaydi: `iss` (emitent), `sub` (subject), `aud` (auditoriya), `exp` (tugash vaqti), `nbf` (shundan oldin yaroqsiz), `iat` (chiqarilgan vaqt), `jti` (identifikator). Bu claim'lar ixtiyoriy, ya'ni ularni tekshirish ilova mantig'i zimmasida: kutubxona sizning o'rningizga qaysi birini majburiy deb hisoblashni bilmaydi.

### Imzo shifrlash emas

Imzolangan JWT maxfiylikni ta'minlamaydi. Base64url kodlash shifrlash emas; token'ni ko'rgan har kim payload'ni o'qiydi. Imzo token'ning o'zgartirilmaganini va (asimmetrik kalit bilan) kim chiqarganini isbotlaydi. Maxfiylik kerak bo'lsa, JWE (shifrlangan token) ishlatiladi yoki ma'lumot token'ga umuman yozilmaydi. Token loglarga, proxy'larga, brauzer storage'ga tushishi mumkin (19-dars), shuning uchun payload'ga telefon raqami, to'liq email yoki ichki identifikator yozmang.

```ts run
const b64u = {
  enc: (bytes: Uint8Array) => btoa(String.fromCharCode(...bytes)).replace(/\+/g, "-").replace(/\//g, "_").replace(/=+$/, ""),
  dec: (s: string) => Uint8Array.from(atob(s.replace(/-/g, "+").replace(/_/g, "/")), (c) => c.charCodeAt(0)),
};
const text = new TextEncoder();
const json = (o: unknown) => b64u.enc(text.encode(JSON.stringify(o)));

const header = json({ alg: "HS256", typ: "JWT" });
const payload = json({ sub: "u1", tenant: "alfa", driverPhone: "+998000000000", exp: 1_700_000_600 });
const fakeSignature = b64u.enc(new Uint8Array(32)); // bu yerda imzoning o'zi muhim emas
const token = `${header}.${payload}.${fakeSignature}`;

// Kalitsiz o'qish:
const decoded = JSON.parse(new TextDecoder().decode(b64u.dec(token.split(".")[1])));
console.log("qismlar soni:", token.split(".").length);
console.log("kalitsiz o'qilgan payload:", decoded);
```

kalitsiz o'qilgan payload: {
  sub: 'u1',
  tenant: 'alfa',

## Chuqurroq: tekshiruv tuzoqlari

### Algoritm token'dan olinmaydi

RFC 8725 talab qiladi: kutubxona chaqiruvchiga qo'llab-quvvatlanadigan algoritmlar to'plamini ko'rsatish imkonini berishi va boshqa algoritmni ishlatmasligi kerak (MUST); `alg` header'i amalda ishlatilgan algoritmga mos bo'lishi ham shart. Sabab: header hujumchi nazoratida. Ikkita klassik hujum:

- `alg: none`. RFC 7519 imzosiz (unsecured) JWT'ni ham ta'riflaydi. RFC 8725 "none" faqat token boshqa yo'l bilan himoyalangan holatlarda maqbul ekanini yozadi. Verifier uni sukut bo'yicha qabul qilsa, hujumchi istalgan payload bilan imzosiz token yasaydi.
- Algoritm chalkashligi. Server asimmetrik imzo (masalan, RS256) kutadi va ochiq kalitni saqlaydi. Agar verifier header'dagi `alg` ga ergashsa, hujumchi `HS256` deb ko'rsatib, ochiq kalitni HMAC maxfiy kaliti sifatida ishlatib "imzo" yasashi mumkin. Mexanizm oddiy: ochiq kalit hammaga ma'lum. Yechim ham oddiy: server algoritmni o'zi tanlaydi va kalit turini algoritmga bog'laydi.

### Claim'larni tekshirish

Imzoning to'g'riligi faqat token o'zgartirilmaganini aytadi. Qolgan hammasini siz tekshirasiz (RFC 7519 7.2 bo'limi va RFC 8725 bo'limlari):

- `exp` va `nbf`: muddat. Muddatsiz token qabul qilinmasin.
- `iss`: kutilgan emitent. Bir nechta emitent ishonchli bo'lsa, har biriga o'z kalitlari bog'langan bo'lsin.
- `aud`: token aynan shu servis uchun. RFC 8725: emitent bir nechta relying party uchun token chiqarsa, `aud` bo'lishi va tekshirilishi shart (MUST); aks holda hujumchi bir servisga berilgan token'ni boshqasida ishlatadi (substitution).
- RFC 8725 yana "olingan claim'larga ishonmaslik" va "aniq turlash" (`typ`) haqida yozadi: turli maqsadlar uchun chiqarilgan token'lar (access token, ID token) bir-biri o'rnida qabul qilinmasligi kerak, ularni o'zaro chiqarib tashlovchi qoidalar bilan ajrating.

### Imzo yoki MAC: kalit kimda bo'lishi kerak

JWT'ni ikki usulda himoyalash mumkin va farq kalit boshqaruvida. Raqamli imzoda (ES256, PS256, EdDSA) emitent shaxsiy kalit bilan imzolaydi, auditoriya esa faqat ochiq kalit bilan tekshiradi: ochiq kalit sir emas, uni HTTPS manzilda e'lon qilish va rotatsiya qilish oson, tekshiruvchi servisdan sir sizib chiqish xavfi yo'q. JSON Web Token Cheat Sheet tavsiya etilgan sxemalarni ko'rsatadi: ES256, PS256 va EdDSA tavsiya etiladi (EdDSA kutubxonalarda cheklangan qo'llab-quvvatlanadi), RSASSA-PKCS1-v1_5 (RS256) esa tavsiya etilmaydi. MAC'da (HS256) emitent va auditoriya bitta umumiy sirni bilishi kerak, shuning uchun har (emitent, auditoriya) juftligi uchun alohida sir bo'lishi shart: bitta sir bir nechta servis bilan ulashilsa, ulardan biri emitentni o'ynab token yasay oladi. MAC faqat emitentning o'zi auditoriya bo'lgan holatda mantiqiy. HMAC siri uchun cheat sheet qoidalari: lokal kriptografik xavfsiz generatordan olinadi, parol emas, kamida 160 bit entropiya, uzunligi hash chiqishidan kam emas (HS256 uchun 256 bit), boshqa maqsadda va boshqa auditoriya yoki emitent bilan qayta ishlatilmaydi. RFC 8725 ham inson eslab qoladigan parolni to'g'ridan-to'g'ri HS256 kaliti sifatida ishlatishni taqiqlaydi (MUST NOT). Yuqoridagi o'quv kodidagi `"server-maxfiy-kalit-32-bayt-uzun!"` aynan shu qoidani buzadi: u o'qiladigan matn, tasodifiy emas. U faqat mexanizmni ko'rsatish uchun; production'da kalitni CSPRNG bilan yarating va maxfiylar ombori orqali bering (69-dars).

Header'dagi boshqa maydonlar ham ishonchsiz kirish: `jwk` (token ichiga joylangan kalit), `jku` va `x5u` (kalit yoki sertifikat URL'i) va `x5c` (sertifikat zanjiri). Verifier kalitni shu maydonlardan olsa, hujumchi o'z kalit juftligini yaratib, ochiq kalitni `jwk`ga yoki o'zi joylashtirgan JWK Set'ga ishora qiluvchi `jku`ga yozadi va o'z shaxsiy kaliti bilan imzolaydi: imzo "to'g'ri" chiqadi. URL orqali olinadigan kalit SSRF yo'liga ham aylanadi (27-dars). Cheat sheet qoidasi: kalitni token'dan olmang, faqat emitent bilan oldindan o'rnatilgan ishonchdan (qattiq belgilangan kalit yoki emitent metadata'sidagi `jwks_uri`) oling. Bu maydonlarning noqonuniy ishlatilishi yo'q: `kid` mavjud, allaqachon sozlangan JWK Set ichidan qaysi kalitni tanlashning normal usuli. Muhimi, ularni ishonch manbai emas, ishonchli to'plam ichidagi ko'rsatkich sifatida ishlating.

### Kalit tanlash va `kid`

Bir nechta imzolash kaliti bo'lganda (rotatsiya paytida eski va yangi kalit birga yashaydi) header'da `kid` (key id) maydoni ishlatiladi. Bu maydon ham hujumchi nazoratida, shuning uchun uni faqat serverdagi ishonchli kalitlar ro'yxatidan qidirish uchun kalit sifatida ishlating: `kid` ni fayl yo'li, SQL so'rovi yoki URL sifatida talqin qilish yangi injection yo'llarini ochadi (21-dars). Ro'yxatda topilmagan `kid` rad etiladi, serverga yangi kalit "yuklab olish" uchun URL qabul qilinmaydi. Har kalit bitta algoritm bilan bog'lanadi: kalit va algoritm juftligi serverda saqlanadi, token'dan olinmaydi. Rotatsiya mexanikasi 68-darsda; bu yerda muhim qoida: eski kalitni olib tashlaganingizda u bilan imzolangan token'lar ham yaroqsiz bo'ladi, shuning uchun access token'ning qisqa umri rotatsiyani osonlashtiradi.

Bir nechta emitentga ishonadigan verifier uchun yana bir tuzoq bor: issuer confusion. Agar verifier kalitni `kid` bo'yicha barcha ishonchli emitentlarning JWK Set'lari birlashmasidan qidirsa, hujumchi `iss` ni kutilgan emitentga, `kid` ni esa boshqa (masalan, hamkor yoki o'zi ro'yxatdan o'tgan) emitentning kalitiga qo'yishi mumkin: imzo shu kalit bilan tekshiriladi va to'g'ri chiqadi, `iss` va `aud` taqqoslashlari ham o'tadi, hech qanday kalit o'g'irlanmagan. Mitigatsiya: `iss` ni butun satr sifatida (sxema va yo'l bilan, katta-kichik harfni farqlab) kutilgan qiymat yoki aniq ruxsat ro'yxati bilan solishtiring, kalit to'plamini faqat tasdiqlangan `iss` ga bog'langan manbadan (shu emitentning `jwks_uri`) oling, `aud` ichida o'z identifikatoringiz borligini tekshiring (satr ham, massiv ham). Ko'p tenantli tizimda ham shunday: barcha tenantlarning kalitlari ichidan qidirmang, kalit to'plamini emitent bo'yicha kalitlangan ro'yxatdan oling. RFC 7519 `iss` va `aud` ni ixtiyoriy qiladi, shuning uchun ularning yo'qligida token'ni rad etish spetsifikatsiya talabi emas, balki joriy qilish qarori; ularsiz verifier kalitni emitentga bog'lay olmaydi va token o'ziga mo'ljallanganini bilmaydi.

### Token turlari va maqsadni ajratish

Bir emitent bir nechta turdagi token chiqaradi: access token, ID token (49-dars), qisqa muddatli bir martalik havola token'i (masalan, email tasdiqlash, 50-dars). Agar ularning hammasi bir xil kalit bilan imzolansa va faqat imzo tekshirilsa, hujumchi bir maqsad uchun olingan token'ni boshqasida ishlatishi mumkin (cross-JWT confusion). RFC 8725 aniq turlash (`typ` va claim'lar to'plami) va turli token turlari uchun o'zaro chiqarib tashlovchi tekshiruv qoidalarini tavsiya qiladi. Amalda: har tur uchun alohida `aud` yoki alohida kalit, va verifier tur uchun majburiy claim'larni talab qiladi (masalan, email tasdiqlash token'ida `purpose: "verify-email"` bo'lmasa, uni sessiya token'i sifatida qabul qilmaslik). Bu muallifning dizayn tavsiyasi, standart faqat tamoyilni beradi.

### Claim'larga qancha ishonish

Token ichidagi `role: "admin"` imzo tufayli o'zgarmagan, lekin dolzarb bo'lmasligi mumkin: xodimning roli o'zgartirilgan, lekin token hali amal qiladi. Shuning uchun token'dagi claim'lar identifikatsiya uchun (kim), nozik authorization qarori uchun esa joriy ma'lumot manbasi (ro'yxatdagi rol, tenant a'zoligi) ishlatilishi kerak. Tenant identifikatori token'da bo'lsa ham, ma'lumot so'rovi filtriga serverda tasdiqlangan qiymat qo'yiladi (55-dars). Token hajmi ham masala: har so'rovda sarlavha bilan yuboriladi, ko'p claim yozilsa trafik va log hajmi oshadi.

### Bekor qilish muammosi

Stateless token ichidagi `exp` o'tmaguncha yaroqli. Foydalanuvchi parolini almashtirgan, xodim bo'shatilgan, token o'g'irlangan bo'lsa, server qo'shimcha holatsiz uni to'xtata olmaydi. Odatiy yechimlar: qisqa muddatli access token (daqiqalar) va serverda saqlanadigan, bekor qilinadigan refresh token; yoki denylist/token versiyasi. Ularning ikkalasi ham server holatini qaytaradi. Denylist'ni `jti` va `iss` juftligi bilan yuriting va yozuvni token `exp` vaqtigacha saqlang. Cheat sheet bitta xavfli xatoga ogohlantiradi: denylist kaliti sifatida xom token yoki uning SHA-256 hash'ini ishlatmang. Yaroqli, lekin boshqa ko'rinishdagi token (qat'iy bo'lmagan parser yoki ECDSA imzosining malleability xossasi tufayli) imzo tekshiruvidan o'tib, bekor qilingan token hash'idan farq qilishi va denylist'ni chetlab o'tishi mumkin. Boshqa variantlar: emitent tomonidan bekor qilish uchun Token Status List (token ichidagi `status` claim'i holat ro'yxatiga ishora qiladi), qayta ishlatishga qarshi qisqa `exp`, yangilik va replay uchun sessiyaga bog'langan `nonce` (OpenID Connect shunday qiladi, 49-dars) va egasiga bog'langan (sender-constrained) access token'lar, masalan DPoP yoki mTLS bilan bog'langan: ular o'g'irlangan token'ni tegishli shaxsiy kalitsiz ishlatishni qiyinlashtiradi, lekin tokenning oshkor bo'lishini to'sa olmaydi. Bu tanlov mexanikasi 46-darsdagi sessiya modeliga o'xshaydi. JWT'ning haqiqiy foydasi: bir nechta mustaqil servis markaziy xotiraga murojaat qilmay, ishonchli emitent chiqargan da'voni imzo orqali tekshirishi.

## Misol: servislar orasidagi token

### Zaif kod

Eski tekshiruv algoritmni token'dan oladi, `none` ni qabul qiladi va faqat imzoni (agar bo'lsa) tekshiradi.

```ts run
const text = new TextEncoder();
const b64u = {
  enc: (bytes: Uint8Array) => btoa(String.fromCharCode(...bytes)).replace(/\+/g, "-").replace(/\//g, "_").replace(/=+$/, ""),
  dec: (s: string) => Uint8Array.from(atob(s.replace(/-/g, "+").replace(/_/g, "/")), (c) => c.charCodeAt(0)),
};
const jsonPart = (o: unknown) => b64u.enc(text.encode(JSON.stringify(o)));
const parse = (s: string) => JSON.parse(new TextDecoder().decode(b64u.dec(s)));

const hmacKey = await crypto.subtle.importKey("raw", text.encode("server-maxfiy-kalit-32-bayt-uzun!"), { name: "HMAC", hash: "SHA-256" }, false, ["sign", "verify"]);

async function sign(claims: object): Promise<string> {
  const data = `${jsonPart({ alg: "HS256", typ: "JWT" })}.${jsonPart(claims)}`;
  const sig = new Uint8Array(await crypto.subtle.sign("HMAC", hmacKey, text.encode(data)));
  return `${data}.${b64u.enc(sig)}`;
}

// ZAIF: alg token'dan olinadi, "none" ruxsat, exp/iss/aud tekshirilmaydi.
async function verifyWeak(token: string): Promise<any | null> {
  const [h, p, s] = token.split(".");
  const header = parse(h);
  if (header.alg === "none") return parse(p);
  if (header.alg === "HS256") {
    const ok = await crypto.subtle.verify("HMAC", hmacKey, b64u.dec(s), text.encode(`${h}.${p}`));
    return ok ? parse(p) : null;
  }
  return null;
}

const t = await sign({ sub: "u1", tenant: "alfa", role: "dispatcher", exp: 1_700_000_600 });
console.log("haqiqiy token:", await verifyWeak(t));
```

```text
haqiqiy token: { sub: 'u1', tenant: 'alfa', role: 'dispatcher', exp: 1700000600 }
```

### Hujum

Hujumchi hech qanday kalitni bilmaydi: u header'da `alg: none` ko'rsatib, istagan payload bilan token yig'adi. Ikkinchi hujum: muddati o'tgan haqiqiy token.

### Tuzatilgan kod

Algoritm serverda qat'iy belgilanadi, imzo har doim tekshiriladi, claim'lar (iss, aud, exp, nbf, sub) alohida tekshiriladi, xato sababi mijozga ochiq qaytarilmaydi.

```ts run
const text = new TextEncoder();
const b64u = {
  enc: (bytes: Uint8Array) => btoa(String.fromCharCode(...bytes)).replace(/\+/g, "-").replace(/\//g, "_").replace(/=+$/, ""),
  dec: (s: string) => Uint8Array.from(atob(s.replace(/-/g, "+").replace(/_/g, "/")), (c) => c.charCodeAt(0)),
};
const jsonPart = (o: unknown) => b64u.enc(text.encode(JSON.stringify(o)));
const parse = (s: string) => JSON.parse(new TextDecoder().decode(b64u.dec(s)));
const hmacKey = await crypto.subtle.importKey("raw", text.encode("server-maxfiy-kalit-32-bayt-uzun!"), { name: "HMAC", hash: "SHA-256" }, false, ["sign", "verify"]);

const ISS = "https://auth.avtopark.example";
const AUD = "telemetry-api";

async function sign(claims: object): Promise<string> {
  const data = `${jsonPart({ alg: "HS256", typ: "JWT" })}.${jsonPart(claims)}`;
  const sig = new Uint8Array(await crypto.subtle.sign("HMAC", hmacKey, text.encode(data)));
  return `${data}.${b64u.enc(sig)}`;
}

async function verifyStrong(token: string, now: number): Promise<Record<string, unknown> | null> {
  try {
    const parts = token.split(".");
    if (parts.length !== 3) return null;
    const [h, p, s] = parts;
    const header = parse(h);
    if (header.alg !== "HS256") return null; // algoritm serverda qat'iy
    const ok = await crypto.subtle.verify("HMAC", hmacKey, b64u.dec(s), text.encode(`${h}.${p}`));
    if (!ok) return null;
    const c = parse(p);
    const auds: unknown[] = Array.isArray(c.aud) ? c.aud : [c.aud];
    if (c.iss !== ISS || !auds.includes(AUD)) return null;
    if (typeof c.exp !== "number" || c.exp <= now) return null;
    if (typeof c.nbf === "number" && c.nbf > now) return null;
    if (typeof c.sub !== "string" || !c.sub) return null;
    return c;
  } catch {
    return null; // buzilgan token xato tashlamaydi, rad etiladi
  }
}

const now = 1_700_000_000;
const good = await sign({ iss: ISS, aud: AUD, sub: "u1", tenant: "alfa", exp: now + 600 });
const expired = await sign({ iss: ISS, aud: AUD, sub: "u1", exp: now - 10 });
const otherAud = await sign({ iss: ISS, aud: "reports-api", sub: "u1", exp: now + 600 });
const forged = `${jsonPart({ alg: "none", typ: "JWT" })}.${jsonPart({ sub: "u9", role: "admin" })}.`;

console.log("haqiqiy:", (await verifyStrong(good, now))?.sub);
console.log("alg=none:", await verifyStrong(forged, now));
console.log("muddati o'tgan:", await verifyStrong(expired, now));
console.log("boshqa servis uchun:", await verifyStrong(otherAud, now));
console.log("buzilgan:", await verifyStrong("abc.def", now));
```

```text
haqiqiy: u1
alg=none: null
muddati o'tgan: null
boshqa servis uchun: null
buzilgan: null
```

Nima uchun yetarli: invariant "token qabul qilinadi faqat serverning kaliti bilan HS256 imzolangan, shu emitent, shu auditoriya va yaroqlilik muddati ichida bo'lsa". `none`, eskirgan va boshqa servis uchun token'lar yopildi. Yopilmagan: bekor qilish (muddati o'tmagan o'g'irlangan token ishlayveradi), kalit sizishi (68-69-darslar), token'ni brauzerda saqlash xavfi (19-dars) va HS256 simmetrik kalit bo'lgani uchun uni bir nechta servis bilan baham ko'rish; ko'p servisli arxitekturada asimmetrik imzo (64-dars) afzal, chunki tekshiruvchi servisda imzolash kaliti bo'lmaydi.

## Qachon qo'llamaslik kerak

Bitta brauzer ilovasi, bitta backend va oddiy login uchun server sessiyasi (46-dars) JWT'dan yaxshiroq: bekor qilish bitta yozuvni o'chirish, token ichida ma'lumot yo'q, algoritm tanlash xatolari yo'q. JWT'ni sessiya sifatida ishlatish "imkoni bor" degan sababga ko'ra xavflarni oshiradi. Qisqa muddatli imzolangan token asosli joylar: servislar orasidagi so'rovlar, uchinchi tomon API'lari, OIDC ID token (49-dars). Ularda ham: token'ga ma'lumotni kamroq yozing; payload'ga kiritilgan huquqlar (role) token muddati tugaguncha eskirgan bo'lishi mumkin, shu sababli nozik huquq qarorlarini serverdagi joriy ma'lumotdan oling (51-dars). Va nihoyat, JWT'ni o'zingiz yozmang: bu darsdagi kod mexanizmni ko'rsatadi, production'da sinalgan kutubxona ishlating va algoritmni majburiy parametr sifatida bering.

## Stack'da: NestJS va Next.js

NestJS'da `@nestjs/jwt` `JwtService.verifyAsync(token, { algorithms: ["HS256"], issuer, audience })` kabi opsiyalarni qo'llab-quvvatlaydi; `algorithms`, `issuer`, `audience` ni har doim aniq bering va `ignoreExpiration` ni tegmang (bu qatorlar tashqi paket API'siga tayanadi; versiyangiz hujjatini tekshiring). Guard ichida token'ni Authorization sarlavhasidan o'qing (cookie'dan o'qisangiz CSRF himoyasi kerak, 36-dars). Kalit sozlamadan keladi (69-dars), kodga yozilmaydi. Next.js'da middleware qisqa imzo tekshiruvini bajarishi mumkin, lekin kalit materialini mijozga bermang va nozik amallarni Server Action ichida qayta tekshiring (58-dars). Access token'ni `localStorage` ga qo'ymang: XSS uni o'qiydi (19-dars); `HttpOnly` cookie yoki xotirada saqlash va refresh token'ni serverdan bekor qilish mumkin bo'lsin.

## Xulosa

- JWT imzolangan konteyner: `header.payload.signature`. Imzo yaxlitlikni beradi, maxfiylikni emas; payload ochiq o'qiladi.
- Algoritmni token'dan emas, serverdan oling (allowlist). `none` va algoritm chalkashligi shu qoida bilan yopiladi (RFC 8725).
- Imzodan keyin `exp`, `nbf`, `iss`, `aud`, `sub` ni alohida tekshiring; `aud` token almashtirishdan himoya qiladi.
- Stateless token'ni muddatidan oldin bekor qilish uchun server holati kerak: bu JWT'ning asosiy narxi.
- Bitta brauzer ilovasi uchun server sessiyasi odatda sodda va xavfsizroq; JWT servislar orasidagi da'volar uchun.
- Maxfiy ma'lumotni payload'ga yozmang va token'ni `localStorage` da saqlamang.
